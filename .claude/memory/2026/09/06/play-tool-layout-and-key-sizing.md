## 2026-09-06 — 演奏台的布局与琴键尺寸

### 起点:用真实 Chrome 量,而不是读代码猜
用户的判断是"所有乐器都应该横向展开撑满窗口"。驱动系统 Chrome 实测四个演奏面 × 三个视口,
得到的数字直接定性了问题:`/play` 在 1280 下占 **47%**、1920 下占 **36%**,
而 `/tune` `/rhythm` `/trace` `/ear` 全都是 **98%**。

### What changed

- **根因是一行 CSS 的遗漏**:其它每个舞台都写了 `grid-column: 1 / -1`
  (`.metro-stage` / `.trace-stage` / `.ear-stage`),唯独 `.play-stage` 没有,
  于是它掉进 `.dashboard` 两列网格的左列。不是设计取舍,是漏写。
- **删掉页面级宽度上限 `width: min(1440px, …)`**。理由从内容推导而非习惯:
  **宽度上限唯一正当的理由是阅读行长**,而这个 app 几乎没有长文本 —— 键盘、指板、
  时频图、拍点格、五线谱全都越宽越好。于是上限移到真正需要它的文字上(`.notice`),
  `.dashboard` 改为 `repeat(auto-fit, minmax(480px, 1fr))`,超过约 1500px 会**多开一列**
  而不是把两列拉稀(1280 仍是两列,不变)。
- **同一个病的第二处:格子数由像素下限决定**。`repeat(auto-fill, minmax(150px, 1fr))`
  让像素下限决定列数,于是调音页的吉他被折成 **5 弦 + 1 个孤儿**、演奏页 14 个音的笛音阶
  被折成错位方阵。**一件乐器的件数是已知且有意义的**(6 弦就是吉他,14 音就是两个八度),
  所以列数改为从数据来的 `--count`。
- **CSS 陷阱(值得单独记):`auto-fit` 的 `minmax()` 里放百分比会退化成 auto**。
  写成 `minmax(max(var(--cell-min), calc(100% / var(--count) - 8px)), 1fr)` 看起来很优雅,
  但**静默失效**,吉他仍然是 5+1。最终用 `repeat(var(--count), minmax(0,1fr))` 直给,
  再用一条手机 media query 允许换行 —— 21 弦古筝铺在 390px 上不是古筝,是一根头发。
- **指板重写为一个通用网格 + 转置矩阵**,横向/纵向只是"哪根轴承载品位",
  是数据不是第二个组件。方向做成持久化设置:首次访问按视口给默认值(电脑横、手机竖),
  之后玩家的选择永远优先。
- **琴键宽度用物理单位设上下限**:`clamp(9mm, 100%/N, 23.5mm)`。
  23.5mm 是真钢琴白键宽度 —— 再宽没有任何收益;9mm 是指尖 —— 再窄点不准。
  实测:2560/1920 → 88.8px(封顶,居中),1280 → 63.3px(铺满),375 → 34px(触底,横向滚)。
  > **2026-09-14 更正**:这里描述的是"房间替玩家决定"时的行为,它现在是**默认值而非全部** ——
  > 两个端点仍是手的(9/23.5mm 不变),但**中间那一段改由玩家定**,见本文件末条。
  **居中必须用 `margin-inline: auto` 而不是 `justify-content: center`** ——
  后者在内容溢出时会把左边缘裁到滚不回去。
- **手机上的两条**:横向滚动条隐藏(它从最紧张的那个面偷走 15px 高度,
  而键盘/指板有八度按钮和"内容明显还在继续"作为提示);**竖向滚动条保留**,
  因为琴颈往下延伸没有别的线索。工具导航从"换行"改成"手机上去掉装饰图标保持单行" ——
  换行给**每一个**手机页面加了 40px,正好是乐器"放得下"和"放不下"的差额。
- 顺带:品位上加了音名、琴枕是一条真实的边、品记标在板上(原来是一片无名方格);
  导航标签从旧名 `Keys` 改回「演奏 / Play」。

### 把检查固化进 smoke(用户提出,且是本轮最有价值的一条)
手工在 Chrome 里量一次很贵,而这些正是"只有浏览器能回答"的问题。新增常驻断言:
`assertStageFillsWidth`(舞台 ≥90% 主区宽)、`assertNoVOverflow`、`assertSingleRow`、
`assertNavFits`(导航不能藏掉一个工具)、白键宽必须落在 34–89px、品位上必须有音名、
转向后音数不变、21 弦古筝一行且不溢出。临时审计脚本随即删除。

期间还修掉 smoke 自身两个真 bug:**spawn 的 vite 的 stderr 被 pipe 却无人读取**,
缓冲区填满后 vite 阻塞,表现为整个测试挂死;以及 Windows 上 `shell: true`
杀掉的是 cmd,真正的 vite 继续占着端口。改为直接用 `process.execPath` 跑 `vite/bin/vite.js`。

### Validation
473 项单测/组件测试全绿;`vue-tsc --noEmit` 干净;`npm run smoke` 桌面 + 移动双视口全绿;
已推送 origin/main,pre-push 钩子创建标签 **v2.10.0**。

### Reusable insight
- **半宽的舞台对单测完全不可见,对用户一眼就是坏的 —— 所以要量**。
  这类几何缺陷没有任何单元测试能发现,唯一的办法是让浏览器测量并断言。
- **同一份数据被第二个消费者用上时,才知道它建模得对不对**。吉他的 8 种调弦在调音器里
  躺了很久,直到指板复用它才证明"每品一个半音"的建模是对的;反过来,
  `auto-fill minmax` 这种"按像素排版"的写法也是直到第二个消费者出现才暴露为错。
- **魔法像素预算只有在有测试量结果时才可接受**。手机琴颈的 `calc(100vh - 440px)`
  在导航高度一变就立刻失准 —— 而 smoke 当场抓到了,并给出了准确的偏差值。
  没有那条断言,这个数字会一直悄悄错下去。
- **约束写成物理单位可以自解释**:`23.5mm` / `9mm` 比 `88px` / `34px` 多带了"为什么是这个数"。

## 2026-09-14 — 键宽交给玩家、纵向键盘改成真正的旋转、音色上到演奏栏

上一条把琴键宽度写成了房间的事(`clamp(9mm, 100%/N, 23.5mm)`)。玩家说"键盘乐器应该要能够调节
单个键宽度":**两个端点是手的,中间那一段不是房间的,是玩家的**。同时修掉纵向键盘的镜像、
把音色 chips 移到演奏栏,并给三档音色建立了可复现的量化手段。

### What changed

- **键宽可调,端点仍是物理常数**。`MIN_WHITE_MM = 9` / `MAX_WHITE_MM = 23.5` 移进
  `play/domain/layout.ts` —— 因为**滑块、store、板的 clamp 三处必须同意**,而 CSS 不能 import 数字;
  于是由组件把它们作为自定义属性交给样式表(`--kbd-min` / `--kbd-max`),`clamp` 留在 CSS 里,
  存下来的宽度因此也被手兜住。`settings.whiteMm: number | null`,`null` = 房间的老答案。
  校验用 `Number.isFinite` 而不是 `typeof === "number"`:`NaN` 会让 `calc()` 非法,
  整条 `width` 声明被丢掉,板会**静默塌成内容宽度**。
- **自适应要能被看见**。控件在会盖住键盘的 sheet 里,所以**读数就是全部反馈**:
  `PianoKeys` 用 ResizeObserver 量自己那块板、以毫米 emit 出来(`px / (96/25.4)`,CSS 的 mm 定义如此),
  `自适应` 开着时滑块就停在真实宽度上 —— 于是第一次拖动是从"当前宽度"接管,而不是跳到没人选过的数字。
  停在一个并非当前值的滑块,正是这个 app 一贯避免的"控件自述其状态"。
- **纵向键盘原来是镜像,不是旋转**。钢琴有铰链端和自由端:黑键贴在铰链那侧,音名在自由端。
  横向时铰链在上边,所以顺时针转 90° 应该把铰链放到**右边**、音名放左边;
  实现却是 `left: 0`,即黑键贴左边 —— 等于从背面看键盘,**手伸向哪个键都差一格**,而且
  **仓库里没有任何测试看得见黑键贴哪边**。于是先写断言 `assertHingeFacesTheFarEdge`
  (量黑键铰链边到板边的距离、音名到自由端的距离),修复前它在纵向板报 215px。
  修法是四条声明(`right: 0` / `padding` 反向 / `row-reverse` / 圆角反向),布局数学一行没动 ——
  "两个方向是同一套几何"这句话对 `place()` 成立,对样式表不成立。
- **音色 chips 从 sheet 移到演奏栏**,紧挨方向 chips。它们不是"换音色菜单"——三档放的都是
  乐器选择器指名的同一件乐器,所以它和方向是同一类问题(眼前是什么、它会怎样),而 sheet 留给
  真正"设一次然后弹"的东西(乐器、调律、键宽、音量)。署名留在 sheet:那里是选音源的地方。
- **演奏栏是 chrome,chrome 是从乐器身上拿走的空间**。375px 上四组加一行提示是两行、不能是三行
  (18% 的屏幕在说这东西是什么)。让位的是控件不需要的词:"Instrument" 挨着 "Piano" 是在说
  "打开乐器面板的 chip" 已经说过的话,"Octave" 夹在 − 和 + 之间也一样;提示本身在手机上挪到控件
  **前面**(写在最后就会被前面所有东西挤到自己一行)。`assertBarRows` 守住预算(电脑 1 行、手机 2 行),
  而且**按堆叠计数**:栏是垂直居中的,同一行的五项 top 各不相同,拿 top 去重会数成五行。
- **顺带修掉一个真 bug:方向键在做两件事**。window 上的八度监听只忽略文本输入框,而获得焦点的
  radio chip 只 `preventDefault()` 不停止冒泡 —— 于是 chip 上按 ArrowRight **既移动了这一组、
  又移了八度**。以前没人发现是因为唯一一组只有两个 chip 而 smoke 是点它。两组共用的规则
  (方向键走到哪个选项、绕回)现在是 `domain/radio.ts`,不再是同样的六行写两遍。

### Validation
567 项单测/组件测试全绿;`vue-tsc --noEmit` 干净;`npm run smoke` 桌面 + 移动双视口全绿,
新断言:`assertHingeFacesTheFarEdge`(两个方向)、键宽读数与屏幕上真实白键宽相差 ≤0.6mm、
拖动滑块键盘真的变宽、`自适应` 能把宽度还回去、`assertBarRows`(1/2 行)。

### Reusable insight
- **"两个方向是同一套几何"要分别对代码和样式表验证**。`place()` 确实只算 top/height,
  但决定铰链在哪的是 CSS 的 `left`/`right` —— 逻辑层看不见的镜像,只有浏览器量得出来。
- **约束写在物理单位里,但"两端是常数"不等于"中间也是常数"**。9mm/23.5mm 是手给的,
  中间那 14.5mm 是房间给的;把后者误当成前者,就把一个选择变成了一个事实。
- **反馈闭环在控件看不见目标时尤其重要**。sheet 盖住键盘 → 读数就是全部;这时"滑块停在真实值"
  不是锦上添花,而是这个控件唯一能诚实工作的方式。
