## 2026-09-14 — 三档音色的电平与接缝

用户:"音色的问题还是很大",以及"你有没有能力比对合成/采样/混合的不同音色?"

### 起点:先承认没有耳朵,再决定用什么代替
这个环境没有音频输出。**"像不像钢琴"我答不了**。但"三档之间差多少 dB、差在哪个时间点、
哪一档的起音更接近录音"是可以算的 —— 而且用户抱怨的正是这个量级上的事。
于是先建工具:`scripts/timbre-report.mjs`(`npm run timbre`),用**这个 app 自己的引擎**
(`createPerformer` / `createVoicePlayer` / 真实模型与 FluidR3 录音)渲进 `OfflineAudioContext`,
输出每档的峰值、起音时间、衰减到 -20dB 的时间、30/300/900ms 的频谱质心、前 16 个谐波,
以及写成一组的等响 WAV 给耳朵 A/B;第二次运行会读上一次的 json 当基线。数字说差在哪,耳朵说要不要紧。

### What changed

- **校音增益从来没有生效过**。`SampledNote.gain` 的注释写着"录音要乘多少才能和一具模型同电平"
  (钢琴 C4 是 6.65×,即 16dB),计算也对 —— 但它被当成 `playBuffer` 的 **velocity** 参数传进去,
  而 velocity 的定义是"这个音被弹得多重",`clamp(velocity, 0, 1)`。6.65 变成 1。
  于是 **采样档比模型低 16dB**;而混合档的整个前提就是"把录音的起音叠在模型上",
  那个起音因此比它要攻击的音低 16dB —— **从 300ms 往后,混合档在数值上就是合成档**。
  修法:增益自己走一条路(`BufferOptions.gain`,不做 0..1 截断),velocity 仍是 velocity。
  实测三档电平差从 12–19dB 变成 **0.0dB**。
- **混合档原本是叠加,而它要的是交叉淡化**。增益修好之后两层同时以满电平起音,而**量出来的**
  模型起音比录音起音高 8dB(拨弦模型的瞬态比它的响度高一截,录音不是),所以这个音的起音
  仍是模型的、录音只在底下垫着 —— 听起来就是"一件乐器被敲了两次"。改成模型在录音淡出的那
  120ms 里淡入,这才是这一档一直写在注释里的那个动作。峰值也从钢琴 C3 的 +0.1dBFS 降到 -3.0。
- **bench 自己量错了指标**。原来比较的是 **peak**,而两端的目标是**响度**(`render.ts` 与
  `soundfont.ts` 都瞄准前 200ms 的同一个 RMS),峰值是被刻意放开的:"拨弦模型的瞬态比它代表的
  录音高一截,把它压平就是削波而不是对齐"。所以报告一直在对一个设计上就不相等的量报警。
  改成 loudness,并保留 peak 在表里。**这条是这一轮最有价值的一步:错的指标会让工具长期说谎。**
- **全量核验**:20 件有录音的乐器 × 3 个音 × 3 档 = 180 次渲染,扫一遍有没有静音、
  起音为 0、t20=0、没有频谱的。结论:**没有一件是坏的**。两条"看起来像坏"的经查都是设计:
  笛子/低音提琴的录音是**平的**(吹奏/拉奏本来就持续),所以"衰减到 -20dB 的时间"没有意义。

### 已知、未改、留给耳朵的三条

1. **录音是固定 3.129s 的循环渲染,一直按着键会在 3.1s 处断掉**。管乐/风琴的录音在 3.05s
   仍有满电平 → 是硬切。测过:每件乐器的录音在某个 lag 上自相关 0.99–1.00,说明 gleitz 的
   文件里**烘进了一段循环**,所以"接下去循环"在物理上可行;但循环长度必须对齐真实周期才不会有
   接缝,而且**衰减型乐器(钢琴)不该循环、持续型(风琴/管乐)才该** —— 这是一条新能力
   (`sustains`)加循环点,是设计题不是修 bug,没有耳朵不该自己定。
2. **钢琴录音的立体声两声道基本不相关**(88 个音里 36 个负相关,平均 0.04;而电钢/风琴是 1.00)。
   单独听没事,**任何单喇叭/单声道求和会损失 5–10dB 的基频并产生梳状滤波** —— 手机上就是
   "又闷又薄"。代价是失去宽度,所以也留给人定。
3. **模型与录音的频谱差得很远**(基频以上各谐波差 10–100dB 量级)。这就是"音色还是不对"的核心,
   但"修"意味着重做 20 个物理模型,且必须靠耳朵判断方向。工具已经就位,基线已经存下。

所以 `playBuffer` 从来没有被单测覆盖过 —— 这也是这个 bug 能活下来的原因);

### Reusable insight
- **拿不到感官时,先造一个能替你说"差多少"的仪器,再让它说真话**。这一轮两次翻车都出在
  指标上:第一次是没量,第二次是量了 peak 而目标其实是响度。
- **一个参数同时承载两个语义,迟早会被另一方的约束吃掉**。增益和力度都叫"多大",
  但一个可以超过 1,一个不能 —— 混在一起,就得到一个静默失效的 16dB 修正。
- **两层的"叠加"和"交接"是两种声音**。同时满电平起音 = 敲两次;交叉淡化 = 一次。
  注释里写的是后者,代码做的是前者,而**只有量峰值/质心才看得出**。
- **假对象实现得越少,越容易让真 bug 活下来**。`playBuffer` 之所以从没被测过,
  只是因为测试用的假 AudioContext 没实现 `playbackRate`。
