## 2026-09-14 — 三档音色的电平与接缝

用户:"音色的问题还是很大",以及"你有没有能力比对合成/采样/混合的不同音色?"

### 起点:先承认没有耳朵,再决定用什么代替
这个环境没有音频输出。**"像不像钢琴"我答不了**。但"三档之间差多少 dB、差在哪个时间点、
哪一档的起音更接近录音"是可以算的 —— 而且用户抱怨的正是这个量级上的事。
于是先建工具:`scripts/timbre-report.mjs`(`npm run timbre`),用**这个 app 自己的引擎**
(`createPerformer` / `createVoicePlayer` / 真实模型与 FluidR3 录音)渲进 `OfflineAudioContext`,
输出每档的峰值、起音时间、衰减到 -20dB 的时间、30/300/900ms 的频谱质心、前 16 个谐波,
以及写成一组的等响 WAV 给耳朵 A/B;第二次运行会读上一次的 json 当基线。数字说差在哪,耳朵说要不要紧。

### What changed

- **校音增益从来没有生效过**。`SampledNote.gain` 的注释写着"录音要乘多少才能和一具模型同电平"
  (钢琴 C4 是 6.65×,即 16dB),计算也对 —— 但它被当成 `playBuffer` 的 **velocity** 参数传进去,
  而 velocity 的定义是"这个音被弹得多重",`clamp(velocity, 0, 1)`。6.65 变成 1。
  于是 **采样档比模型低 16dB**;而混合档的整个前提就是"把录音的起音叠在模型上",
  那个起音因此比它要攻击的音低 16dB —— **从 300ms 往后,混合档在数值上就是合成档**。
  修法:增益自己走一条路(`BufferOptions.gain`,不做 0..1 截断),velocity 仍是 velocity。
  实测三档电平差从 12–19dB 变成 **0.0dB**。
- **混合档原本是叠加,而它要的是交叉淡化**。增益修好之后两层同时以满电平起音,而**量出来的**
  模型起音比录音起音高 8dB(拨弦模型的瞬态比它的响度高一截,录音不是),所以这个音的起音
  仍是模型的、录音只在底下垫着 —— 听起来就是"一件乐器被敲了两次"。改成模型在录音淡出的那
  120ms 里淡入,这才是这一档一直写在注释里的那个动作。峰值也从钢琴 C3 的 +0.1dBFS 降到 -3.0。
- **bench 自己量错了指标**。原来比较的是 **peak**,而两端的目标是**响度**(`render.ts` 与
  `soundfont.ts` 都瞄准前 200ms 的同一个 RMS),峰值是被刻意放开的:"拨弦模型的瞬态比它代表的
  录音高一截,把它压平就是削波而不是对齐"。所以报告一直在对一个设计上就不相等的量报警。
  改成 loudness,并保留 peak 在表里。**这条是这一轮最有价值的一步:错的指标会让工具长期说谎。**
- **全量核验**:20 件有录音的乐器 × 3 个音 × 3 档 = 180 次渲染,扫一遍有没有静音、
  起音为 0、t20=0、没有频谱的。结论:**没有一件是坏的**。两条"看起来像坏"的经查都是设计:
  笛子/低音提琴的录音是**平的**(吹奏/拉奏本来就持续),所以"衰减到 -20dB 的时间"没有意义。
- **顺带发现的第三个真问题:和弦会撞天花板**。单音峰值在 -8dBFS,而玩家不会只弹一个音 ——
  实测五音和弦已经贴顶,十个音**要到的比存在的多 3dB**,声卡只能用削平高峰来回答,那就是
  "和弦听起来坏了"的嘎吱声;而且三档都一样(模型与录音被有意校准到同一响度)。
  修法是在引擎输出上放一个 limiter(`DynamicsCompressorNode`),而**不是**把主音量调小:
  调小会改掉每一个音的听感,包括那九个从来不是问题的音。实测单音只压 0.04dB、五音 0.25dB、
  十音把输出按在 -2dBFS(修前是要 +3)。这条链路只有真 AudioContext 里才存在,
  所以 `tests/audio-engine.test.ts` 用一个假 context 把它搭出来看。

## 2026-09-14(第二轮)— 把"全部音色"做成可以逐条核验的清单

第一轮修完电平与接缝之后,继续做**端到端核验**:20 件有录音的乐器 × C2–C6 五个音 × 三档
= **300 次渲染**,逐条检查 音高 / 电平 / 是否静音 / 是否削顶。结果是又抓出四个真 bug,
全部是"只有量才看得见"的那一类。

### What changed

- **重采样方向反了**。`SampledNote.offset` 是"录音相对所要求音符的位置"(录音更高时为正),
  而播放速率写成了 `2^(offset/12)` —— 正好是倒数。录音比目标高三个半音,应该**放慢**三个半音,
  不是加快。它一直没暴露,是因为**指数恒等于 1**:钢琴 88 个音的 offset 全是 0,吉他和尤克里里
  也是。它只在**音库没有那个音**时咬人:低音提琴被要求弹 C5 时库内最近的录音在 15 个半音以下,
  于是它给出的音**比目标低了 1.5 个八度**(实测 -1101 cents;被速率 clamp 收拾成 -300)。
  修完后**每件乐器每个音都在 15 cents 以内**。
- **拉伸超过八度的录音已经不是那件乐器**。速率方向修正后,低音提琴被要求弹 C6 就成了
  "把低音提琴重采样 27 个半音"—— 那是大提琴,再往上就是小提琴。`withinReach` 拒绝
  距离超过八度的录音,于是回落**到模型**(这一档本来就有的兜底),音高从差三个半音变成精确。
- **钢琴录音的左右声道不是同一个信号的两份**。它在整库上相关 0.04,88 个音里 36 个**负相关**;
  电钢与风琴都是 1.00。戴耳机那是"宽度",而**手机是把两个声道电学求和的** —— 求和就是梳状滤波,
  实测基频损失 5–10dB,C6 以上连基频都没了。现在**声道不一致就只留更响的那一个**;
  一致的一对原样不动,所以另外两台键盘毫无变化。
- **音库的最后一个采样不一定是静音**。吹奏的音到文件末尾仍是满电平,于是"到此为止"就是从满电平
  跳到零 —— 一声咔哒,出现在一个本来没问题的音的结尾。让出最后 20ms。

### 仍然已知、且这一轮没动的

1. **录音是固定 3.129s 的循环渲染,一直按着键会在 3.1s 处断掉**。管乐/风琴的录音在 3.05s
   仍有满电平。测过:每件乐器的录音在某个 lag 上自相关 0.99–1.00,说明 gleitz 的文件里
   **烘进了一段循环**,所以"接下去循环"在物理上可行;但循环长度必须对齐真实周期才不会有接缝,
   而且**衰减型乐器(钢琴)不该循环、持续型(风琴/管乐)才该** —— 这是新能力(`sustains`)
   加循环点,是设计题不是修 bug,没有耳朵不该自己定。
2. ~~**擦弦模型基本上是噪声,不是弦**~~ —— **已修,见下一节**。
3. **模型与录音的频谱差**(基频以上各谐波差 10–100dB 量级)依旧。工具与基线已就位。

### Validation
554→567 项单测全绿(`tests/audio-voice.test.ts` 的假 context 原来**根本没有 playbackRate**,
所以 `playBuffer` 从来没有被单测覆盖过 —— 这也是这个 bug 能活下来的原因);
`vue-tsc --noEmit` 干净;`npm run smoke` 双视口全绿;bench 全量 180 例。

### 在 dev server 里"隔空摸到 app 自己的模块"有坑(踩了两次,值得单独记)
想在页面里量 app 自己的状态(`peekContext()` / limiter),`page.evaluate` 里 `import()` 的
**不是** app 正在用的那份模块:
- `/src/audio/context.ts` 与 `/src/audio/context.js` 在 Vite dev 下是**两个模块实例**
  (实测 `tsIsJs: false`),各有一份 `engine`;
- 更隐蔽的是 **HMR**:编辑过的模块会被导入方以 `/src/x.ts?t=1699…` 引用,
  于是"重新载入页面"也拿不到 app 那一份,`peekContext()` 一直是 null。
- 可靠做法是**驱动 UI,再读模块**:真实点一次琴键(或 `keyboard.down`)让 app 自己建图,
  然后 `import` 只用来**看**结果。同一份探针里若还要用 `soundfont` 等模块自己造数据,
  必须与自己一致地全用 `.js` 或全用 `.ts`,否则每个模块都是双份。

### Reusable insight
- **拿不到感官时,先造一个能替你说"差多少"的仪器,再让它说真话**。这一轮两次翻车都出在
  指标上:第一次是没量,第二次是量了 peak 而目标其实是响度。
- **单音测量掩盖多音问题**。所有涉及"电平"的结论如果只测一个音,就看不见叠加后的天花板;
  这个 bug 从模型被校准成同一响度那天就在,`npm run timbre` 一次只看一个音也看不见它,
  是"玩家不会只弹一个音"这句常识把它翻出来的。
- **一个参数同时承载两个语义,迟早会被另一方的约束吃掉**。增益和力度都叫"多大",
  但一个可以超过 1,一个不能 —— 混在一起,就得到一个静默失效的 16dB 修正。
- **两层的"叠加"和"交接"是两种声音**。同时满电平起音 = 敲两次;交叉淡化 = 一次。
  注释里写的是后者,代码做的是前者,而**只有量峰值/质心才看得出**。
- **假对象实现得越少,越容易让真 bug 活下来**。`playBuffer` 之所以从没被测过,
  只是因为测试用的假 AudioContext 没实现 `playbackRate`。

### 这一轮的核验口径(可以照抄的命令与判据)

**300 次渲染**(20 件有录音的乐器 × C2/C3/C4/C5/C6 × 三档),四条判据,全部用 app 自己的引擎:
- **不静音**:峰值 > -80dBFS。**不做削顶**:峰值 ≤ 0dBFS。结果:0 静音、0 削顶。
- **音高**:用 **app 自己的 YIN** 去听 app 自己刚弹的音(a 100ms 处的 8192 采样窗),
  与目标频率比。模型族 0–2 cents;录音族 0–30 cents,偏移来自录音本身的揉弦/走音。
  先用"最强的谱峰"或"只在 ±1200 cents 里找最大谐波能量"都会误判:前者会把第二谐波
  当基频(低音区常见),后者**永远偏向低八度**(任何在 f0/2 有能量的频谱都得分更高 ——
  风琴的 16 尺拉杆就是),所以拟合必须**只向上找**。
- **自相似度**:把渲染在"周期 lag"处的归一化自相关当"这段声音有多像一个音"。拨弦 1.000,
  擦弦 0.78,噪声类接近 0 —— 这一条不判对错,它判的是"这段声音到底是不是一个乐音"。
- 判据本身也会说谎:**用 peak 判电平**会对着一个设计上就不相等的量报错(目标是响度);
  **用"最强谱峰"判音高**会把第二谐波判成走音 1200 cents。两次都是判据错,不是被测对象错。

### Reusable insight(补)
- **"只在出问题时才起作用"的代码路径,只有构造出那个问题才验得到**。重采样方向那条 bug
  在每件"音库齐全"的乐器上指数恒为 1 —— 想验它必须**要求一个音库里没有的音**。
  核验清单要按"边界"设计(音域两端、库的尽头),不能只在中间取样。
- **共用的常量如果对所有使用者都一样,它就没被检验过**。`bow: {0.5, 0.4}` 七件乐器一字不差,
  而它们的测量结果也一字不差(2.6%)—— 这不是"统一的音色",这是"没人为任何一件调过"。

## 2026-09-14(第三轮)— 弓不是噪声源,是摩擦

第二轮把这条留给了耳朵:"调到什么程度算对必须靠耳朵"。实际上它有一半是可以量的 ——
**"这段声音是不是一个乐音"不是审美问题**,于是可以修。

### 症状(都是量出来的)
同一段 261Hz 渲染,拨弦族的自相似度 **1.000**、音高误差 0 cents;擦弦族 **0.78**;
能量落在谐波列上的比例:拨弦 **22%**、擦弦 **2.6%**(管乐的 4% 是设计如此)。
更硬的一条:**擦弦的音高测不准** —— C6 的"基频"在不同估计器之间游走 ±30 cents,
因为信号大部分不是谐波。七件乐器共用 `bow: {0.5, 0.4}` 而测量结果一字不差。

### 根因
弓被实现成**环内一个饱和衰减器**:`fed = fed/(1+|fed|)`。衰减器放在谐振腔里
**不会设定电平,它会杀掉共振**:环路每一圈的净增益恒小于 1,因此弦自身永远衰减,
听者听到的是**被谐振腔过滤过的弓噪**。弓压、弓噪两个参数里,真正决定声音的是"噪声有多大",
而注释写的却是"弓噪是音色的一点颜色"。

### 修法:摩擦 = 负阻尼
松香**抓住走得慢的弦、放过走得快的弦**,所以弓把能量送进弦**已经在走的方向** ——
这是环路自身的**增益**,不是旁边的噪声源。三个关键决定:

- **按"电平"读,不按"采样"读**。逐采样地套摩擦曲线是在**重塑每一个波形周期**(等于失真);
  把同一条曲线读成**当前振幅**,就只改环路增益、完全不碰波形 —— 环里跑的仍是弦自己的运动,
  这才是"乐音"的来源。振幅用**峰值跟随器**(快起慢落)取,否则波峰会被放过去几倍。
- **弓的强度写成"弦自身损耗的倍数"**。弓只有在**远超**损耗时才"说得出来":
  刚够付损耗的弓要三秒才起音,那是渐强不是音符。所以 `BOW_DRIVE` 是倍数,
  而不是一个没人能核对量纲的裸数字(这一轮为此走了两次弯路)。
- **摩擦曲线必须在"这个弓压值多少振幅"附近陡峭**。太缓的曲线在小振幅处就用完了,
  于是弦要么三秒渐强、要么直接冲顶。`BOW_LEVEL` = 满压值多少振幅(`pressure × 它`),
  `BOW_SHARPNESS` = 曲线多陡。

### 顺带:阻尼是"音色平衡"不是"衰减"
弦乐是**被持续驱动**的,所有分音都处于稳态、谁都不衰减 —— 所以 `damping` 在这里是
**平衡**而非衰减,而 0.36–0.46 是**拨弦**的数字。录音自己的亮度给了标尺:
小提琴的频谱质心从 C2 的 264Hz 升到 C6 的 2480Hz;把 damping 降到 **0.08**,
C3/C4 处模型与录音的质心差从 20dB 收到几个百分点。

### 结果(用 app 自己的引擎、app 自己的 YIN 量)
七件擦弦乐器:**谐波能量 94–129%、自相似度 1.00、音高 0–1 cents**、约 0.3 秒起音、
不削顶。全量 **300 次渲染:0 静音、0 削顶**;每件乐器音高都在 ~30 cents 以内。

### 两个判据的坑(第二次踩)
- "自相似度"要取**绝对值**:风琴/班卓这类**奇次谐波为主**的波形在"一个周期"处是
  **反相**的(相关 -1、音高被读成低八度)—— 那不是走音,是波形本来就是反周期的。
- 窄带测谐波对**有弥散(stiffness)的模型不公平**:不谐和的泛音会跑出测量带宽,
  于是模型被读得比实际更暗。修阻尼时是靠**质心**而不是靠窄带谐波比才定下来的。

### Reusable insight(三)
- **"这不是我能判断的"要再切一刀**:"像不像小提琴"不行,但"这是不是一个乐音"可以 ——
  后者有客观判据(自相似度、谐波占比、音高可测性),而它恰好覆盖了缺陷的全部。
  把问题切到可判定的那一半,剩下的才是真的需要耳朵。
- **一个物理机制被实现成它的反面时,参数怎么调都救不回来**。饱和器 vs 负阻尼:
  两者都能"限制电平",但一个杀掉共振、一个产生共振。看参数表(弓压 0.5、弓噪 0.4)
  完全看不出这一点,只有量输出才知道。
- **单位的量纲要说出来**。同一个常数"弓有多强"在两次尝试里分别差了三个数量级,
  因为没人说清它是"每圈的增益"还是"损耗的倍数"。
