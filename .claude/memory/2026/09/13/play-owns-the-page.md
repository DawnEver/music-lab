## 2026-09-13 — 演奏页拥有整个页面,以及四个面都能转向

### 起点:三条用户判断 + 一条 bug 报告
「横向和纵向必须要填满整个页面,现在被卡片限制住了」「所有乐器都要支持更换横向/纵向」
「更换乐器的选项在卡片上方,现在在下方」「乐器音色现在不对啊!请逐个检查」。

### What changed

- **`.play-stage` 不再是 `.card`**。上一轮把它修到占满宽度,但卡片本身还有
  `padding: 22px`、圆角、边框、面板背景 —— 这些全部是从乐器身上扣的。
  现在它是一条从导航到页脚之间、**横竖都归乐器**的裸舞台,
  `.dashboard:has(.play-stage) { grid-template-rows: auto minmax(0, 1fr) }`
  把剩下的高度全给舞台。新增 `.play-stage > * { flex: 1 1 auto; min-height: 0 }` ——
  **新加一个演奏面不需要写任何布局 CSS**,这是"填满"能持续成立的原因。
- **选择器移到舞台上方**,和方向、八度、提示凑成一条 `.play-bar`。
  踩到的坑:`.card` 会 `overflow: hidden` 并建立层叠上下文,chip row 一直放在卡片外;
  现在位置换了,**sheet 默认向上弹**,于是弹到了视口外面。修法不是给演奏页特判,
  而是让 `ControlSheet` 自己决定方向:`anchor.top < innerHeight / 2` 就向下弹。
  **"控件被搬到页面别处,它的编辑器就跟到有空间的那一侧"** 是一条能自解释的规则。
- **第二个坑:`.play-bar` 的 `z-index: 2` 和黑键的 `z-index: 2` 打平**,
  后出现的 DOM(乐器)赢了,sheet 被琴键吃掉点击。改成 5。
- **方向从"指板方向"变成"方向"**:`fretOrientation` → `orientation`,
  存档里读一次旧键就丢掉。四个面各自转置:
  琴键横→`left/width`、竖→`top/height`(同一个 `keyboardLayout`,一个 style 对象);
  鼓组按 `column` 而非 `row` 分组;笛子音阶从一行变一列;指板本来就是矩阵。
- **鼓组纵向的第一版是错的,而且 unit test 看不出来**:`.pad-grid` 本身是
  `flex-direction: column`,我又把 `.pad-row` 也设成 column,于是**列也被堆起来了** ——
  DOM 里还是 5 行、每行件数也对,屏幕上是九行单件,鼓组被折成了一张列表。
  修法是让 grid 在纵向时改成 `row`。smoke 里加的断言不看数量看几何:
  **各行的 `x` 必须互不相同**。
- **笛子的"填满"第一版也是错的**:卡片被拉高 640px,而音孔还是挤在中间 110px 里,
  看起来就是"被拉长的小部件"。改成音名在顶、六个孔 `space-evenly` 铺满整张卡片 ——
  **笛子本来就是一个管子上开六个孔,铺满才是它本来的样子**。
  填满本身不是目的,"填满之后像什么"才是。
- **修掉一个真 bug:鼓组九个 pad 全是正弦"哔"**。`Performer.strike()` 走的是
  `VoicePlayer.hold()`,而 `hold()` 只认振荡器 —— `waveform: "noise"` 被
  `? "sine" : ...` 静默降级。军鼓因此是 1900Hz 纯正弦。`play()` 有一条噪声分支、
  测试也覆盖了,**但 `hold()` 那条路径从来没人测过**。现在两条路径都建 buffer source。
- 顺手删掉了手机端琴颈的 `max-height: calc(100vh - 440px)` ——
  舞台现在用 flex 知道自己的高度,这个魔法数字没有存在的理由了。

### 发现但没有修的既有缺陷:`/trace` 手机端溢出 17px
`git stash` 后在干净工作树上同样复现,确认与本轮改动无关。
375×667 且有麦克风设备时,`.audio-source` 从 67px 涨到 113px,
`.shell` 变成 684px,整页超出 17px。**这首歌只有一句副歌**:
"picture 画布必须有 200px,而 chrome 就是多出来那一截"。
没有顺手修,因为怎么砍是另一个工具的设计决定(砍按钮、砍设备选择器、还是砍电平表),
应该先问。已告知用户。

### Validation
479 项单测/组件测试全绿;`vue-tsc --noEmit` 干净;桌面 smoke 全绿(含新的演奏页断言)。
移动端 smoke 被上面那条既有 `/trace` 缺陷挡在演奏页之前,所以**另外用真实 Chrome
在六个视口(1920/1280/1024/768/375/320)单独量了演奏页**:宽 100%、底部差 0px、
无横竖溢出、白键 34–89px、四个面两个方向全部通过。临时脚本随即删除。

### Reusable insight
- **"填满"是一个几何问题,也是一个设计问题**。高度给到卡片不等于乐器用上了高度:
  内容居中会让它读成"被拉长的部件"。真正要做的是找到这个乐器**在真实世界里
  怎么占据它那根轴**(笛子是管子上的六个孔),然后让内容沿那根轴展开。
- **同一个数值出现在两个地方,就一定会有一天打平**。`.play-bar` 和黑键都是 `z-index: 2`,
  谁在上面由 DOM 顺序决定 —— 这种耦合不会报错,只会让一个控件莫名其妙点不动。
- **DOM 数量对、几何错,是组件测试的盲区**。鼓组折叠那次,`.pad-row` 的数量、
  每行的件数、每件的 id 全都对。只有"各行 x 各不相同"这种几何断言能抓到它。
- **未测试的那条分支不会自己暴露**。`hold()` 和 `play()` 是同一份 spec 的两个消费者,
  噪声支持只加在了其中一个上,而测试恰好只覆盖了那一个。消费者多于一个时,
  **共通的能力要问两遍**。
